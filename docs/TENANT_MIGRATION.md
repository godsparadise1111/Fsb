# راهنمای مهاجرت امن به Tenant

## هدف و اصل عدم تخریب
این مهاجرت هیچ سازمان قدیمی را به‌صورت خودکار به یک مشتری متصل نمی‌کند. در محیط‌هایی که چند مشتری یا چند سازمان وجود دارد، انتخاب Tenant از روی نام، کد، تاریخ ایجاد یا حدس اپراتور مجاز نیست. سازمان بدون `tenantId` تا زمان تعیین مالک تجاری آن، دادهٔ legacy محسوب می‌شود و باید از عملیات مشتری‌محور مسدود بماند.

## ترتیب اجرای عملیاتی
1. از PostgreSQL نسخهٔ پشتیبان کامل بگیرید و بازیابی آن را در محیط جداگانه بررسی کنید.
2. فایل `apps/api/database/migrations/20261107_001_tenant_membership_and_safe_legacy_scope.sql` را روی نسخهٔ staging اجرا کنید.
3. تعداد Tenantها، سازمان‌های بدون Tenant و عضویت‌ها را ثبت کنید.
4. با مالک کسب‌وکار هر سازمان، مشتری حقوقی/قراردادی مربوط را تأیید کنید.
5. برای هر مشتری یک Tenant مستقل بسازید و وضعیت را فقط پس از تکمیل اطلاعات قرارداد به `ACTIVE` تغییر دهید.
6. برای هر سازمان، فقط با شناسه‌های تأییدشده دستور UPDATE جداگانه اجرا کنید. از یک UPDATE عمومی برای تمام سازمان‌های بدون Tenant استفاده نکنید.
7. کاربران را به Tenant مربوط اضافه کنید و حداقل یک مدیر فعال برای هر مشتری تعیین کنید.
8. گزارش کنترل تطبیق را تهیه کنید: سازمان‌های بدون Tenant، سازمان‌های هر Tenant، تعداد اعضا، مدیران فعال و وضعیت Tenant.
9. پس از تأیید مالک داده، همین روند را در محیط اصلی با پنجرهٔ نگهداری و backup تازه اجرا کنید.

## عضویت و مدیر مشتری
- `POST /api/platform/tenants/:tenantId/members` با `userId` و اختیاری `isTenantAdmin`
- `GET /api/platform/tenants/:tenantId/members`
- `PATCH /api/platform/tenants/:tenantId/members/:userId/admin` با `isTenantAdmin`
- `DELETE /api/platform/tenants/:tenantId/members/:userId`
- حذف یا تنزل آخرین مدیر فعال مشتری ممنوع است.
- ایجاد و مدیریت عضویت فعلاً از مسیر مدیریت پلتفرم انجام می‌شود؛ گردش دعوت ایمیلی، پذیرش دعوت و خودخدمتی مدیر مشتری در مرحلهٔ بعدی تکمیل می‌شود.

## زمینهٔ احراز هویت
در درخواست‌های کاربران عضو مشتری، هدر `X-Tenant-Id` برای انتخاب مشتری فعال استفاده می‌شود. این مقدار به‌تنهایی مجوز نیست: API عضویت فعال همان کاربر را از پایگاه داده بررسی می‌کند و وضعیت Tenant را نیز کنترل می‌کند. اگر کاربر فقط عضو یک Tenant باشد، زمینه به‌صورت خودکار انتخاب می‌شود؛ اگر چند عضویت داشته باشد، انتخاب صریح لازم است. Tenant تعلیق‌شده یا بسته در احراز هویت رد می‌شود.

## کنترل دسترسی و محدودیت‌های فعلی
- نقش پلتفرمی همچنان تنها راه دسترسی به عملیات `tenants.*` است.
- مدیر مشتری فقط در زمینهٔ Tenant تأییدشده و برای درخواست‌هایی که سازمان آن صریحاً مشخص و متعلق به همان Tenant است، دسترسی مدیریتی می‌گیرد.
- نقش سازمانی بدون زمینهٔ Tenant تأییدشده معتبر نیست.
- تلاش برای استفاده از شناسهٔ سازمان متعلق به Tenant دیگر رد می‌شود.
- مسیرهای مبتنی بر شناسهٔ منابع فرزند (مانند بعضی مسیرهای نسخه، کارتابل و تاریخچه) هنوز به پوشش کامل tenant-aware نیاز دارند؛ تا تکمیل آن، عرضهٔ SaaS و دسترسی عمومی توصیه نمی‌شود.
- تعلیق Tenant در هر درخواست احراز هویت‌شده با زمینهٔ آن Tenant اعمال می‌شود؛ اما endpointهای عمومی/توکن‌محور آینده، jobها، فایل‌ها، صف‌ها و دسترسی‌های خارج از HTTP نیز باید در طراحی نهایی پوشش داده شوند.

## کنترل نهایی پس از مهاجرت
```sql
SELECT id, name, code FROM organizations WHERE "tenantId" IS NULL;
SELECT "tenantId", count(*) FROM organizations GROUP BY "tenantId";
SELECT "tenantId", count(*) FILTER (WHERE "isActive") AS active_members,
       count(*) FILTER (WHERE "isActive" AND "isTenantAdmin") AS active_admins
FROM tenant_memberships GROUP BY "tenantId";
SELECT id, name, status FROM tenants ORDER BY name;
```

مهاجرت فقط وقتی خاتمه‌یافته تلقی می‌شود که هر سازمان legacy یا به‌صورت مستند تعیین تکلیف شده باشد یا در فهرست استثناهای مورد تأیید باقی بماند. اجرای SQL یا تیک مستندات به‌تنهایی اثبات‌کنندهٔ صحت داده نیست.
