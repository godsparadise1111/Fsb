# راهنمای مهاجرت امن به Tenant

## هدف و اصل عدم تخریب
این مهاجرت هیچ سازمان قدیمی را به‌صورت خودکار به یک مشتری متصل نمی‌کند. در محیط‌هایی که چند مشتری یا چند سازمان وجود دارد، انتخاب Tenant از روی نام، کد، تاریخ ایجاد یا حدس اپراتور مجاز نیست. سازمان بدون `tenantId` تا زمان تعیین مالک تجاری آن، دادهٔ legacy محسوب می‌شود و باید از عملیات مشتری‌محور مسدود بماند.

## ترتیب اجرای عملیاتی
1. از PostgreSQL نسخهٔ پشتیبان کامل بگیرید و بازیابی آن را در محیط جداگانه بررسی کنید.
2. فایل `20261107_001_tenant_membership_and_safe_legacy_scope.sql` را روی staging اجرا کنید؛ این مرحله فقط ساختار Tenant و عضویت را می‌سازد و دادهٔ قدیمی را خودکار تخصیص نمی‌دهد.
3. تعداد Tenantها، سازمان‌های بدون Tenant و عضویت‌ها را ثبت کنید.
4. با مالک کسب‌وکار هر سازمان، مشتری حقوقی/قراردادی مربوط را تأیید کنید.
5. برای هر مشتری یک Tenant مستقل بسازید و وضعیت را فقط پس از تکمیل اطلاعات قرارداد به `ACTIVE` تغییر دهید.
6. برای هر سازمان، فقط با شناسه‌های تأییدشده دستور UPDATE جداگانه اجرا کنید. از یک UPDATE عمومی برای تمام سازمان‌های بدون Tenant استفاده نکنید.
7. کاربران را به Tenant مربوط اضافه کنید و حداقل یک مدیر فعال برای هر مشتری تعیین کنید.
8. گزارش کنترل تطبیق را تهیه کنید: سازمان‌های بدون Tenant، سازمان‌های هر Tenant، تعداد اعضا، مدیران فعال و وضعیت Tenant.
9. پس از تأیید مالک داده و اطمینان از اینکه هیچ سازمان legacy بدون Tenant باقی نمانده، migration `20261107_002_tenant_composite_integrity.sql` را اجرا کنید. این مرحله با وجود حتی یک سازمان بدون Tenant عمداً متوقف می‌شود و برای رکوردهای فرزند Tenant را backfill و قیود مرکب ایجاد می‌کند.
10. سپس migration `20261107_003_tenant_membership_workflow_integrity.sql` را اجرا کنید تا انتساب‌های جدید وظایف و عملیات گردش‌کار به عضویت فعال همان مشتری وابسته شوند.
11. migration `20261107_004_tenant_invitations.sql` را برای ذخیره دعوت‌های یک‌بارمصرف، هش توکن، تاریخ انقضا و سوابق پذیرش/لغو اجرا کنید.
12. پیش از migration پنجم، تمام کاربران دارای انتساب سمت یا نقش سازمانی فعال را به Tenant صحیح عضو کنید. migration `20261107_005_tenant_scoped_identity_assignments.sql` انتساب‌های فعال فاقد عضویت متناظر یا نقش‌های ناسازگار با دامنه را شناسایی می‌کند و در صورت وجود آن‌ها متوقف می‌شود؛ سپس tenant-aware کردن انتساب سمت کاربران و نقش‌های سازمانی را اعمال کنید.
13. migration `20261107_006_tenant_membership_invariants.sql` را اجرا کنید تا فعال‌بودن کاربر و Tenant برای عضویت جدید، تغییرناپذیری هویت عضویت و حفظ آخرین مدیر فعال در سطح دیتابیس تضمین شود.
14. migration `20261107_007_revoke_memberships_on_user_deactivation.sql` را اجرا کنید تا غیرفعال‌سازی حساب کاربر، عضویت‌های Tenant او را نیز در همان تراکنش غیرفعال کند؛ اگر این کار آخرین مدیر فعال یک مشتری را حذف کند، کل عملیات رد می‌شود.
15. migration `20261107_008_revoke_tenant_identity_assignments.sql` را اجرا کنید تا غیرفعال‌شدن عضویت، سمت‌ها و نقش‌های سازمانی همان Tenant را نیز لغو کند؛ فعال‌سازی دوباره عضویت، مجوزهای قبلی را خودکار برنمی‌گرداند.
16. کلید `FSB_OUTBOX_ENCRYPTION_KEY` را با `openssl rand -hex 32` بسازید و خارج از Git در Secret Manager/محیط اجرا قرار دهید؛ این کلید برای رمزگشایی payloadهای صف اعلان حیاتی است.
17. migration `20261107_009_notification_outbox.sql` را اجرا کنید تا صف پایدار و tenant-scoped اعلان‌ها ایجاد شود. این migration فقط جدول و صف را می‌سازد؛ worker SMTP در کد آماده است اما باید در پردازه جداگانه با تنظیمات SMTP و کلید رمزگذاری فعال شود.
18. migration `20261107_010_tenant_audit_logs.sql` را اجرا کنید تا تاریخچهٔ append-only اقدامات مدیریتی Tenant با actor و target ثبت شود.
19. migration `20261107_011_tenant_scoped_file_attachments.sql` را برای جدول پیوست‌های خصوصی اجرا کنید؛ این مرحله به composite key پاسخ فرم در migration 002 وابسته است و Tenant را از پاسخ والد استخراج می‌کند و عضویت فعال بارگذار را در دیتابیس الزام می‌کند.
20. migration `20261107_012_reporting_indexes.sql` را برای بهینه‌سازی پرس‌وجوهای گزارش‌گیری فرایند و سن وظایف اجرا کنید؛ این migration فقط ایندکس می‌سازد و داده را تغییر نمی‌دهد.
21. migration `20261107_013_workflow_task_sla_deadlines.sql` را اجرا کنید تا ستون مهلت وظیفه و ایندکس وظایف دارای مهلت فعال ایجاد شود.
22. migration `20261107_014_task_delegations.sql` را برای تاریخچه تفویض زمان‌دار وظایف اجرا کنید.
23. migration `20261107_015_task_deferral_approval.sql` را برای درخواست تعویق مهلت، تأیید/رد و قیود Tenant اجرا کنید.
24. migration `20261107_016_organization_substitutions.sql` را برای جانشینی زمان‌دار سازمانی، مجوز مدیریت و کنترل‌های Tenant اجرا کنید.
25. migration `20261107_017_workflow_sla_reassignment.sql` را برای تاریخچه بازتخصیص خودکار SLA و وضعیت `REASSIGNED` در انتساب‌ها اجرا کنید.
26. تمام مراحل را ابتدا روی staging و با backup قابل بازیابی تمرین کنید؛ پس از تأیید مالک داده، در محیط اصلی با پنجرهٔ نگهداری و backup تازه اجرا کنید.

## عضویت و مدیر مشتری
- `POST /api/platform/tenants/:tenantId/members` با `userId` و اختیاری `isTenantAdmin`
- `GET /api/platform/tenants/:tenantId/members`
- `PATCH /api/platform/tenants/:tenantId/members/:userId/admin` با `isTenantAdmin`
- `DELETE /api/platform/tenants/:tenantId/members/:userId`
- حذف یا تنزل آخرین مدیر فعال مشتری ممنوع است.
- مدیر پلتفرم می‌تواند عضویت را مستقیم ایجاد کند؛ مدیر مشتری نیز از مسیرهای `/api/tenant/members` و `/api/tenant/invitations` اعضا را مدیریت و دعوت کند.
- `GET /api/tenant/audit-logs` تاریخچهٔ اقدامات مدیریتی مشتری را برای مدیران Tenant نمایش می‌دهد؛ رکوردها در دیتابیس append-only هستند.
- دعوت‌شده‌ای که حساب دارد باید با همان ایمیل وارد شود و دعوت را بپذیرد؛ فرد فاقد حساب می‌تواند از مسیر ثبت‌نام دعوت، حساب بسازد. ایمیل از دعوت استخراج می‌شود و قابل تغییر نیست.
- ایجاد دعوت، رویداد ایمیل را در همان تراکنش در Outbox رمزگذاری‌شده ثبت می‌کند؛ پاسخ API دیگر توکن خام را برنمی‌گرداند. کلید `FSB_OUTBOX_ENCRYPTION_KEY` الزامی است.
- سرویس Outbox امکان claim اتمیک با `SKIP LOCKED`، lease دو دقیقه‌ای، تأیید تحویل و retry نمایی تا ۱۰ تلاش را فراهم می‌کند. Worker مستقل SMTP پیاده‌سازی شده و پس از تنظیم SMTP و کلید رمزگذاری در پردازه جداگانه اجرا می‌شود؛ API مدیریت پیام‌های مرده نیز موجود است.

## زمینهٔ احراز هویت
در درخواست‌های کاربران عضو مشتری، هدر `X-Tenant-Id` برای انتخاب مشتری فعال استفاده می‌شود. این مقدار به‌تنهایی مجوز نیست: API عضویت فعال همان کاربر را از پایگاه داده بررسی می‌کند و وضعیت Tenant را نیز کنترل می‌کند. اگر کاربر فقط عضو یک Tenant باشد، زمینه به‌صورت خودکار انتخاب می‌شود؛ اگر چند عضویت داشته باشد، انتخاب صریح لازم است. Tenant تعلیق‌شده یا بسته در احراز هویت رد می‌شود.

## کنترل دسترسی و محدودیت‌های فعلی
- نقش پلتفرمی همچنان تنها راه دسترسی به عملیات `tenants.*` است.
- مدیر مشتری فقط در زمینهٔ Tenant تأییدشده و برای درخواست‌هایی که سازمان آن صریحاً مشخص و متعلق به همان Tenant است، دسترسی مدیریتی می‌گیرد.
- نقش سازمانی بدون زمینهٔ Tenant تأییدشده معتبر نیست.
- تلاش برای استفاده از شناسهٔ سازمان متعلق به Tenant دیگر رد می‌شود.
- مسیرهای مبتنی بر شناسهٔ منابع فرزند (مانند بعضی مسیرهای نسخه، کارتابل و تاریخچه) هنوز به پوشش کامل tenant-aware نیاز دارند؛ تا تکمیل آن، عرضهٔ SaaS و دسترسی عمومی توصیه نمی‌شود.
- تعلیق Tenant در هر درخواست احراز هویت‌شده با زمینهٔ آن Tenant اعمال می‌شود؛ اما endpointهای عمومی/توکن‌محور آینده، jobها، فایل‌ها، صف‌ها و دسترسی‌های خارج از HTTP نیز باید در طراحی نهایی پوشش داده شوند. پیوست‌های فرم در migration 011 به Tenant و پاسخ والد مقید شده‌اند؛ فایل‌ها در volume خصوصی با کلید تصادفی نگهداری می‌شوند، اما اسکن بدافزار، lifecycle حذف و backup/restore هنوز نیازمند تکمیل عملیاتی است.

## قیود سطح پایگاه داده
Migration دوم برای process/form definitions و versions، process instances، workflow tasks، action logs و submissions ستون Tenant و Foreign Key مرکب ایجاد می‌کند. Triggerها Tenant را از والد معتبر استخراج می‌کنند و ارجاع بین مشتریان را رد می‌کنند. Migration سوم برای task assignees همین کنترل را اعمال می‌کند و درج/تغییر بازیگران جدید گردش‌کار و ثبت پاسخ را به عضویت فعال در Tenant مربوط وابسته می‌کند. Migration پنجم نیز tenantId انتساب سمت و نقش سازمانی را از سازمان مرجع استخراج می‌کند و با Trigger و Foreign Key مرکب، انتساب به کاربر غیرفعال یا خارج از Tenant را رد می‌کند؛ پیش از اجرا، تطبیق عضویت تاریخی کاربران دارای انتساب فعال الزامی است. Migration ششم قواعد عضویت و آخرین مدیر را در PostgreSQL اعمال می‌کند. Migration هفتم نیز با غیرفعال‌سازی حساب، همه عضویت‌های Tenant را لغو می‌کند و اگر آخرین مدیر فعال باشد، با کمک قید مهاجرت ششم تراکنش را rollback می‌کند. Migration هشتم با لغو عضویت، انتساب سمت‌ها و نقش‌های همان Tenant را نیز غیرفعال می‌کند؛ بازگرداندن عضویت نیازمند تخصیص مجدد صریح سمت و نقش است. Migration نهم جدول Outbox رمزگذاری‌شده با مالکیت Tenant، کلید یکتای dedupe و ایندکس صف را ایجاد می‌کند. Migration دهم تاریخچهٔ append-only عملیات مدیریتی مشتری را ذخیره می‌کند. Migration یازدهم پیوست‌ها را به پاسخ فرم و Tenant والد با Foreign Key مرکب متصل می‌کند و عضویت فعال بارگذار را در زمان درج کنترل می‌کند. Migration دوازدهم ایندکس‌های لازم برای گزارش‌های Tenant و پایش سن وظایف را اضافه می‌کند. Migration سیزدهم ستون `dueAt` و ایندکس وظایف مهلت‌دار را اضافه می‌کند. Migration چهاردهم تاریخچه تفویض زمان‌دار را با قید Tenant و کنترل عضویت طرفین اضافه می‌کند؛ لغو تفویض حتی پس از بسته‌شدن وظیفه یا پایان عضویت مجاز می‌ماند. Migration پانزدهم درخواست تعویق مهلت را با FK مرکب Tenant، یک درخواست باز برای هر وظیفه، جزئیات تغییرناپذیر، کنترل عضویت درخواست‌دهنده/بررسی‌کننده و سقف ۳۰ روز اضافه می‌کند. Migration شانزدهم جانشینی زمان‌دار در سطح سازمان را با FK مرکب، کنترل عضویت و سمت طرفین، جلوگیری از بازه‌های هم‌پوشان و ثبت مجوز مدیریت ایجاد می‌کند؛ اعتبار عضویت/سمت جانشین هنگام مشاهده کارتابل و اقدام نیز دوباره بررسی می‌شود. Migration هفدهم وضعیت تاریخی `REASSIGNED` و جدول تغییرناپذیر تاریخچه بازتخصیص خودکار SLA را اضافه می‌کند؛ worker مستقل آن فقط پس از فعال‌سازی صریح اجرا می‌شود و پیش از فعال‌سازی باید migration اعمال شده باشد. Migration هجدهم نوع محرک `INACTIVE_ASSIGNEE` را اضافه می‌کند و یکتایی تاریخچه را به ترکیب وظیفه/محرک تغییر می‌دهد تا بازتخصیص ناشی از SLA و غیرفعال‌شدن کاربر بتوانند مستقل ثبت شوند. مسیر دوم فقط با `reassignOnInactiveAssignee: true` و گیرندگان `reassignUserIds` در تعریف مرحله فعال می‌شود؛ حساب، عضویت Tenant و سمت سازمانی گیرندگان در لحظه انتقال دوباره بررسی می‌شود. اگر گیرنده‌ای نامعتبر باشد، انتقال انجام نمی‌شود و مسئولیت قبلی بی‌جهت حذف نخواهد شد. Migration نوزدهم جدول `organization_absences` را با Tenant، سازمان، کارمند غایب، جانشین و رکورد جانشینی پشتیبان مرتبط می‌کند؛ ثبت غیبت و جانشینی در یک تراکنش است و لغو غیبت، جانشینی را نیز لغو می‌کند. پایان طبیعی بازه از طریق شرط زمانی جانشینی، دسترسی را خاتمه می‌دهد و سوابق اقدام را نگه می‌دارد. رکوردهای تاریخی حفظ می‌شوند؛ این migrationها به‌تنهایی عضویت تاریخی کاربران را بازسازی نمی‌کنند. Migration بعدی `20261109_001_organization_workload_policies.sql` سیاست ظرفیت جانشین را به تفکیک Tenant/سازمان ایجاد می‌کند؛ محدودیت سقف به‌صورت پیش‌فرض خاموش است، بازهٔ مجاز سقف ۱ تا ۵۰۰ وظیفه و آستانه هشدار ۱ تا ۱۰۰ درصد است و تغییر سیاست فقط توسط عضو فعال همان Tenant قابل ثبت است.


- 20261109_016_workflow_action_idempotency.sql: ذخیرهٔ پایدار کلید idempotency برای اقدام وظیفه با دامنهٔ Tenant/وظیفه/کاربر، hash درخواست، پاسخ نهایی و FK مرکب Tenant؛ رکوردهای تکمیل‌شده تغییرناپذیرند و برای replay پاسخ حذف نمی‌شوند؛ migration همچنین assignmentهای Pending باقی‌مانده روی وظایف terminal را REASSIGNED می‌کند و lifecycle eventهای اقدام تاریخی را از action logها backfill می‌کند. این migration باید پیش از انتشار نسخه‌ای که هدر `Idempotency-Key` را اجباری می‌کند اعمال شود.


- 20261109_017_workflow_recovery_incidents.sql: ثبت پایدار رخدادهای بازیابی فرایند با fingerprint یکتا، جزئیات تغییرناپذیر و وضعیت OPEN/ACKNOWLEDGED/RESOLVED؛ پس از migrationهای 015 و 016 اجرا شود. این جدول برای فرایندهای RUNNING بدون وظیفهٔ فعال یا دارای چند وظیفهٔ فعال و فرایندهای terminal با وظیفهٔ باز، مسیر پیگیری اپراتوری فراهم می‌کند.

## کنترل نهایی پس از مهاجرت
```sql
SELECT id, name, code FROM organizations WHERE "tenantId" IS NULL;
SELECT "tenantId", count(*) FROM organizations GROUP BY "tenantId";
SELECT "tenantId", count(*) FILTER (WHERE "isActive") AS active_members,
       count(*) FILTER (WHERE "isActive" AND "isTenantAdmin") AS active_admins
FROM tenant_memberships GROUP BY "tenantId";
SELECT id, name, status FROM tenants ORDER BY name;
```

مهاجرت فقط وقتی خاتمه‌یافته تلقی می‌شود که هر سازمان legacy یا به‌صورت مستند تعیین تکلیف شده باشد یا در فهرست استثناهای مورد تأیید باقی بماند. اجرای SQL یا تیک مستندات به‌تنهایی اثبات‌کنندهٔ صحت داده نیست.

## تکمیل‌های امنیتی و عملیاتی پس از مهاجرت‌های پایه

مهاجرت‌های زیر نیز باید به ترتیب شماره و پس از پیش‌نیازهای پایه، روی staging تمرین و سپس با backup قابل بازیابی اعمال شوند:

- 20261109_001_organization_workload_policies.sql: سیاست ظرفیت جانشین برای هر سازمان.
- 20261109_002_operational_alert_lifecycle.sql و 20261109_003_operational_alert_events.sql: چرخه عمر هشدار عملیاتی، تخصیص، تأیید، حل و تاریخچه رویدادها.
- 20261109_004_operational_alert_sla.sql، 20261109_005_operational_alert_sla_timeline.sql، 20261109_006_operational_alert_sla_policies.sql و 20261109_007_operational_alert_sla_reporting_indexes.sql: مهلت پاسخ/حل هشدار، سیاست SLA سازمانی، timeline و ایندکس گزارش.

## کنترل‌های تکمیلی Tenant Isolation

- مسیر کارتابل مستقیم علاوه بر انتساب باز، عضویت فعال Tenant، حساب فعال و سمت معتبر فعلی در سازمان را بررسی می‌کند.
- مسیرهای تفویض و جانشینی نیز پیش از نمایش/اقدام، عضویت و سمت معتبر کاربر را مجدداً بررسی می‌کنند.
- بارگذاری، فهرست و دانلود پیوست باید هم‌زمان با Tenant پاسخ فرم و Tenant سازمان فرم تطبیق داشته باشند؛ Trigger دیتابیس نیز کاربر بارگذار فعال و عضو فعال Tenant را الزام می‌کند و درج هم‌زمان با غیرفعال‌سازی سازمان را serialize می‌کند.
- Worker بازتخصیص SLA در تراکنش، مالکیت Tenant وظیفه و فعال‌بودن Tenant را دوباره کنترل می‌کند؛ Worker اعلان نیز پیش از تحویل، وضعیت Tenant و اعتبار گیرنده را بررسی می‌کند.
- تحویل دعوت باید با ایمیل ثبت‌شده روی همان دعوت تطبیق داشته باشد؛ تطبیق صرف شناسه دعوت و Tenant کافی نیست.

این کنترل‌ها در کد و migration آماده شده‌اند، اما تا زمانی که migrationها در staging اجرا و آزمون‌های cross-tenant، worker و restore با شواهد ثبت نشده‌اند، پذیرش عملیاتی یا آمادگی SaaS تأییدشده محسوب نمی‌شود.

- 20261109_012_identity_database_invariants.sql: آخرین مدیر را با شمارش حساب‌های فعال و قفل Tenant حفظ می‌کند؛ غیرفعال‌سازی حساب را به لغو عضویت و سپس نقش/سمت‌های Tenant متصل می‌کند؛ Foreign Key مرکب انتساب سمت و نقش را به عضویت همان Tenant می‌بندد؛ ساخت/فعال‌سازی انتساب را در برابر غیرفعال‌شدن هم‌زمان حساب، عضویت، Tenant، سازمان، واحد، سمت یا نقش serialize می‌کند؛ و با غیرفعال‌سازی ساختار سازمانی، انتساب‌های وابسته را لغو می‌کند. این migration اگر Tenant فاقد مدیر فعال باشد عمداً متوقف می‌شود و پیش از اجرا باید مدیر معتبر تعیین شود.

اسکریپت scripts/migrate-onprem.sh نیز هر فایل migration و درج checksum آن در ledger را در یک تراکنش PostgreSQL اجرا می‌کند؛ در نتیجه crash بین commit تغییرات schema و ثبت ledger باعث اجرای مجدد ناقص migration نخواهد شد. checksum فایل‌های قبلاً اجراشده همچنان کنترل می‌شود.
- 20261109_013_organization_structure_integrity.sql: Foreign Key مرکب والد واحد را به همان سازمان محدود می‌کند؛ چرخه در درخت واحدها و انتقال واحد/سمت بین سازمان‌ها را رد می‌کند؛ ایجاد/فعال‌سازی واحد و سمت را به والد، سازمان و Tenant فعال وابسته می‌کند؛ و غیرفعال‌سازی سازمان را به غیرفعال‌سازی واحدها، سمت‌ها و انتساب‌های وابسته cascade می‌کند. فعال‌سازی مجدد والد، فرزندان و انتساب‌های قبلی را خودکار احیا نمی‌کند.

## فعال‌سازی مشتری و مدیر اولیه

Tenant جدید در وضعیت `PENDING` ساخته می‌شود. فعال‌سازی آن باید با `PATCH /api/platform/tenants/:id/status` و بدنهٔ `status: ACTIVE` به‌همراه `initialAdminUserId` انجام شود، مگر اینکه Tenant از قبل مدیر فعال داشته باشد. تغییر وضعیت و ایجاد/ارتقای عضویت مدیر اولیه در یک تراکنش است. PostgreSQL در پایان تراکنش فعال‌بودن حداقل یک مدیر با حساب فعال را کنترل می‌کند؛ Tenant فعال بدون مدیر قابل ایجاد یا باقی‌ماندن نیست. پیش از اعمال migration 012، Tenantهای فعال فاقد مدیر باید تعیین تکلیف شوند.


## چرخه عمر پس از لغو دسترسی و نگهداشت

Migration 015 وضعیت `CANCELLED` را برای درخواست تعویق اضافه می‌کند. لغو عضویت، تفویض‌های مرتبط را باطل و درخواست تعویق معلقِ ثبت‌شده توسط همان عضو را لغو می‌کند؛ رویدادهای مرتبط با وظایف در `workflow_task_lifecycle_events` ثبت می‌شوند. وظایف دارای مسئول نامعتبر توسط worker بازبینی می‌شوند: اگر fallback معتبر تعریف شده باشد، مسئول جایگزین می‌شود؛ در غیر این صورت مسئول نامعتبر از مجموعه مسئولان فعال خارج و اگر مسئول معتبر دیگری نمانده باشد وظیفه لغو می‌شود.

غیرفعال‌سازی سازمان یا بستن قطعی Tenant، وظایف باز را لغو، انتساب‌های Pending را به حالت تاریخی `REASSIGNED` منتقل، تفویض‌ها و درخواست‌های تعویق باز را خاتمه و اعلان‌های Outbox در صف را برای Tenant بسته‌شده DEAD می‌کند. Tenant بسته‌شده قابل فعال‌سازی مجدد نیست.

سیاست نگهداشت در `docs/DATA_RETENTION.md` تعریف شده است. هیچ‌یک از این مسیرها حذف فیزیکی تاریخچه وظایف، رویدادهای چرخه‌عمر، گزارش حسابرسی یا فایل‌های پیوست را انجام نمی‌دهند.

## اتمیک‌بودن اقدام گردش‌کار و Idempotency
- مسیر `POST /api/tasks/:id/actions` اکنون هدر `Idempotency-Key` با ۱۶ تا ۱۲۸ نویسهٔ امن می‌خواهد؛ کلید باید برای هر اقدام منطقی یکتا و در retry همان درخواست ثابت بماند.
- همان کلید با payload یکسان، پاسخ ذخیره‌شده را برمی‌گرداند؛ استفادهٔ مجدد از کلید با payload متفاوت با `409 Conflict` رد می‌شود. کلید در محدودهٔ Tenant، وظیفه و کاربر مستقل است.
- درج کلید، ثبت action log، تغییر assignment/task/process، ساخت وظیفهٔ مرحلهٔ بعد یا بازگشت و درج اعلان assignment در Outbox در یک تراکنش PostgreSQL انجام می‌شوند؛ شکست هر بخش کل عملیات را rollback می‌کند.
- Worker اعلان هنگام ارسال، بازبودن وظیفه، pending بودن assignment، عضویت فعال Tenant، سمت سازمانی و ایمیل معتبر گیرنده را دوباره بررسی می‌کند؛ اعلان نامعتبر به‌جای ارسال به DEAD می‌رود.
- Workerهای SLA و غیرفعال‌بودن مسئول، ابتدا Tenant و سازمان و سپس وظیفه را قفل می‌کنند؛ همهٔ مسیرهای اقدام کاربر نیز همین ترتیب قفل را رعایت می‌کنند.
- کلاینت باید `Idempotency-Key` را قبل از ارسال تولید و تا دریافت پاسخ قطعی نگهداری کند؛ برای retry شبکه‌ای کلید جدید نسازد.


- 20261109_018_workflow_recovery_incident_events.sql: جدول append-only تاریخچهٔ تلاش‌های Worker، تأیید رسیدگی، بستن رخداد و درخواست Replay ردشده را ایجاد می‌کند. این migration باید بعد از 017 اجرا شود؛ سپس پنل `/recovery-incidents` و APIهای `/api/workflow/recovery-incidents` قابل استفاده‌اند. Tenant از زمینهٔ احراز هویت استخراج می‌شود و Tenant Admin فقط به رخدادهای همان Tenant دسترسی دارد.


## سلامت عملیاتی پلتفرم و Registry امن Replay

- مسیر `GET /api/platform/workflow-health` فقط با مجوز پلتفرمی `tenants.read` در دسترس است؛ این مسیر Tenant جاری را از ورودی نمی‌گیرد و فقط برای مدیر پلتفرم نمای تجمیعی می‌سازد.
- پنل `/platform-workflow-health` شاخص‌های Tenantهای فعال، فرایندها، وظایف، رخدادهای بازیابی، صف اعلان‌ها و سیگنال‌های Worker را نشان می‌دهد. پنل مشتری نیز از `GET /api/tenant/dashboard` تعداد رخدادهای باز، رخدادهای بسته‌شده در ۲۴ ساعت و آخرین مشاهده Worker را دریافت می‌کند.
- نبود `WORKER_SCAN` در ۱۵ دقیقه، به‌تنهایی اثبات خرابی Worker نیست؛ ممکن است در آن بازه رخداد واجد شرایطی وجود نداشته باشد. مقدار env فقط پیکربندی Worker را نشان می‌دهد و سیگنال مشاهده‌شده از تاریخچه رخدادها جدا گزارش می‌شود.
- `WorkflowRecoveryReplayRegistry` یک allow-list درون‌برنامه‌ای است. Handler باید system-only، idempotent، دارای idempotency key اجباری و فاقد امکان اقدام انسانی یا پیشبرد مرحله باشد. ثبت Handler تکراری برای یک نوع رخداد رد می‌شود.
- Registry در حال حاضر عمداً خالی است. حتی در صورت ثبت Handler، endpoint اجرای Replay تا زمان تکمیل executor تراکنشی و receipt پایدار idempotency fail-closed باقی می‌ماند. بنابراین در این نسخه هیچ عملیات Replay واقعی اجرا نمی‌شود و هیچ migration جدیدی برای این قابلیت لازم نیست.
- مدیر پلتفرم برای مشاهده داشبورد باید نقش PLATFORM با مجوز `tenants.read` داشته باشد. مدیر Tenant فقط داشبورد همان Tenant را می‌بیند؛ API تجمیعی برای نقش Tenant ارائه نمی‌شود.


- گزارش `GET /api/tenant/reports/overview` و خروجی `overview.csv` نیز شاخص‌های رخدادهای بازیابی را در بازهٔ انتخابی و فیلتر سازمانی ارائه می‌کنند: تعداد رخدادهای ایجادشده، وضعیت فعلی cohort، رخدادهای بسته‌شده در بازه، میانگین زمان رسیدگی، تفکیک دو نوع رخداد، تلاش‌های Worker، تأییدها، بستن‌ها و Replayهای ردشده.
