# موتور گردش کار و فرایندهای F-S

## وضعیت فعلی

موتور موجود در ماژول‌های Process و Workflow تکمیل می‌شود؛ موتور موازی یا مدل دیتابیس تکراری ساخته نشده است. تعریف فرایند، نسخه‌بندی و انتشار، نمونه فرایند، وظایف، کارتابل شخصی، تخصیص چندنفره، اقدام تراکنشی، تفویض، جانشینی، SLA، بازتخصیص و تاریخچه از قبل وجود داشتند.

## مدل مرحله و تخصیص

هر نسخه منتشرشده در `process_versions.schema` دارای آرایه `steps` است. هر مرحله می‌تواند این ویژگی‌ها را داشته باشد:

- `title`: عنوان مرحله.
- `instructions`: دستور اقدام.
- `assigneeUserIds`: شناسه کاربران مسئول مرحله؛ برای مراحل بعد از مرحله شروع اجباری است. در گراف صریح برای همه مراحل لازم است.
- `assignmentPolicy`: یکی از `ALL_ASSIGNEES` یا `ANY_ASSIGNEE`.
- `dueInHours`: مهلت SLA.
- تنظیمات escalation و reassignment موجود، مطابق اعتبارسنجی انتشار.

سیاست `ALL_ASSIGNEES` زمانی کامل می‌شود که همه تخصیص‌های فعال تأیید شوند. در سیاست `ANY_ASSIGNEE` اولین تأیید، وظیفه را کامل و تخصیص‌های باقی‌مانده را با وضعیت REASSIGNED می‌بندد. رد یک مسئول به‌صورت فوری مسیر رد را اجرا می‌کند.

## گراف انتقال صریح

برای نسخه‌های جدید، می‌توان در کنار `steps` آرایه اختیاری `transitions` تعریف کرد. هر قانون دقیقاً یک مبدأ، اقدام و مقصد دارد:

```json
{
  "steps": [
    {
      "title": "ثبت و بررسی اولیه",
      "assigneeUserIds": ["11111111-1111-4111-8111-111111111111"],
      "assignmentPolicy": "ALL_ASSIGNEES"
    },
    {
      "title": "تأیید مدیر",
      "assigneeUserIds": ["22222222-2222-4222-8222-222222222222"],
      "assignmentPolicy": "ANY_ASSIGNEE"
    },
    {
      "title": "بایگانی",
      "assigneeUserIds": ["33333333-3333-4333-8333-333333333333"],
      "assignmentPolicy": "ALL_ASSIGNEES"
    }
  ],
  "transitions": [
    { "fromStepIndex": 0, "action": "APPROVED", "toStepIndex": 1 },
    { "fromStepIndex": 0, "action": "REJECTED", "toStepIndex": null },
    { "fromStepIndex": 1, "action": "APPROVED", "toStepIndex": 2 },
    { "fromStepIndex": 1, "action": "REJECTED", "toStepIndex": 0 },
    { "fromStepIndex": 1, "action": "RETURNED", "toStepIndex": 0 },
    { "fromStepIndex": 2, "action": "APPROVED", "toStepIndex": null },
    { "fromStepIndex": 2, "action": "REJECTED", "toStepIndex": 1 },
    { "fromStepIndex": 2, "action": "RETURNED", "toStepIndex": 1 }
  ]
}
```

قواعد انتشار گراف:
- حداکثر ۱۰۰ مرحله و ۳۰۰ انتقال.
- هر مرحله باید از مرحله صفر قابل دسترس باشد.
- برای هر مرحله دقیقاً یک انتقال APPROVED تعریف می‌شود.
- برای هر ترکیب مرحله/اقدام بیش از یک قانون مجاز نیست.
- مقصد باید شماره مرحله معتبر و متفاوت از مبدأ یا `null` برای پایان/رد نهایی باشد.
- مقصد RETURNED باید حتماً مرحله‌ای قبل از مبدأ باشد.
- حداقل یک انتقال APPROVED باید به `null` ختم شود تا مسیر تکمیل وجود داشته باشد.
- همه مراحل باید مسئول معتبر در schema داشته باشند؛ اعتبار عضویت Tenant، کاربر فعال و سمت معتبر هنگام ایجاد وظیفه نیز دوباره بررسی می‌شود.

اگر `transitions` تعریف نشود، رفتار قدیمی حفظ می‌شود: APPROVED به مرحله بعدی می‌رود، REJECTED فرایند را لغو می‌کند و RETURNED مقصد قبلی را از درخواست می‌گیرد. اگر گراف صریح تعریف شود، مقصد APPROVED و RETURNED از گراف منتشرشده پیروی می‌کند؛ رد بدون یال REJECTED مسیر نهایی لغو محسوب می‌شود.

## API کارتابل

- `GET /api/tasks/my`: کارتابل ورودی کاربر؛ فقط وظایف قابل اقدام با تخصیص مستقیم، تفویض یا جانشینی معتبر.
- `GET /api/process-instances/my`: کارتابل خروجی/فرایندهایی که کاربر آغاز کرده است؛ حداکثر ۱۰۰ مورد اخیر.
- `GET /api/process-instances/:id`: جزئیات فرایند و وظایف آن، فقط برای آغازگر یا مشارکت‌کننده مجاز.
- `POST /api/process-instances`: شروع فرایند با تخصیص اولیه.
- `POST /api/tasks/:id/actions`: اقدام APPROVED/REJECTED/RETURNED با هدر اجباری `Idempotency-Key`.
- `GET /api/tasks/:id/history` و `GET /api/tasks/:id/lifecycle`: تاریخچه اقدام و رویدادهای چرخه عمر.

## امنیت و ممیزی

- Tenant از JWT و عضویت جاری پایگاه داده استخراج/تأیید می‌شود؛ `tenantId` بدنه مرجع امنیت نیست.
- سازمان از مالکیت رکورد در پایگاه داده تعیین می‌شود و منابع بین سازمان‌ها قابل ترکیب نیستند.
- شروع فرایند، تخصیص اولیه و ایجاد وظایف مرحله بعدی، عضویت فعال Tenant، کاربر فعال و سمت معتبر در سازمان را کنترل می‌کنند.
- عملیات اقدام با قفل وظیفه و idempotency key در تراکنش انجام می‌شود؛ استفاده مجدد از کلید با payload متفاوت Conflict می‌دهد.
- رویداد اقدام و تغییر وضعیت، تاریخچه Workflow و Tenant Audit در همان تراکنش ثبت می‌شوند.
- Outbox اعلان تخصیص وظیفه در همان تراکنش ساخته می‌شود و Worker ایمیل هنگام ارسال، عضویت و سمت جاری دریافت‌کننده را دوباره اعتبارسنجی می‌کند.

## وضعیت اعتبارسنجی

کد گراف انتقال، کارتابل خروجی و Audit در Git ثبت شده است؛ هنوز Build، تست خودکار، Migration، تست مرورگر یا آزمون دو Tenant در Staging اجرا نشده‌اند. تا پایان این آزمون‌ها، موتور گردش کار برای Production تأییدشده تلقی نمی‌شود.
